## Runtime comercial desplegado: diferencia verificada

El 26/10/2026 UTC se verificó por HTTPS el contrato desplegado, que conserva version=0.10.1 pero publica CommercialInstanceCreate, GET /v1/plans y GET /v1/images. El repositorio local anterior no contiene esa revisión. Se conserva el snapshot público exacto en contracts/iacp-deployed-20261026.json; IaCoC reconoce el $ref efectivo de creación y rechaza referencias desconocidas, sin suponer compatibilidad por el número de versión.

| Capacidad comercial desplegada | Método y endpoint                  | Contrato / controles                                                                                                                                                                                                                                  |
| ------------------------------ | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Productos                      | GET /v1/plans                      | PlanResponse[]; plan_id, nombre, CPU/MiB/GiB, availability.available/capacity_verified/reasons por tenant                                                                                                                                             |
| Imágenes                       | GET /v1/images                     | ImageResponse[]; SO, versión, certificación/habilitación, compatibilidad, autorización y disponibilidad; null conserva capacidad desconocida                                                                                                          |
| Crear comercial                | POST /v1/instances                 | CommercialInstanceCreate: name, plan_id, image_id, access.root_password; network lab-dhcp y start_on_create explícitos; commercial_context opcional, sin fabricar order_id. Idempotency-Key, propiedad, cuotas comerciales y capacidad física en IACP |
| Lifecycle comercial            | rutas de energía/DELETE existentes | No exige inventar self_service_policy_id; se consulta mutations_available y el backend IACP verifica el vínculo comercial y fences                                                                                                                    |

En este contrato IaCoC utiliza exclusivamente productos comerciales, nunca sustituye un producto bloqueado con la ruta de creación por perfil histórico. Los límites de esos perfiles se muestran como evidencia técnica separada; no se aplican como derechos comerciales en la GUI ni en el preflight comercial del servidor. La GUI presenta la elegibilidad publicada; cada nueva intención se envía a IACP, sin preflight local de cuota o capacidad. Si el servidor solo publica InstanceCreate, se conserva el flujo histórico de perfiles/políticas 0.10.1 con su propio cuerpo y parámetros; IACP decide sus límites, sin presupuestos calculados por IaCoC.

## Carencias y contrato mínimo solicitado

- CT/LXD no está publicado. El runtime actual sí publica productos KVM; la ausencia de catálogo comercial aplica únicamente al snapshot antiguo del repositorio local. No fabricar precios ni IDs comerciales.
- ProfileResponse no acredita capacidad física; en el contrato comercial se usa availability de /v1/plans e /v1/images y el SO publicado. Los límites comerciales numéricos no se publican en esos contratos: se muestran los códigos exactos de bloqueo, sin inventar máximos desde un perfil. Conviene publicar derechos/consumo comercial separados de capacidad física y política de seguridad.
- No hay introspección de identidad/scopes. Solicitar GET /v1/identity que publique subject, tenant_id, roles, purposes, administration y allowed_actions. IaCoC verifica tenant mediante observabilidad y exige confirmación administrativa de credencial operator dedicada sin administration; IACP autoriza cada solicitud. No se afirma verificar scopes no publicados.
- No hay autorización por recurso para cada botón ni inventario energético agregado. Se cruzan política vigente y PowerState; IACP conserva decisión definitiva. Overview no infiere energía del status de provisión.
- No hay SSE publicado ni garantía de eventos sin pérdida. Polling acotado de lectura con backoff; sin reenvío automático de comandos.
- No hay restauración: recrear abre un aprovisionamiento nuevo sin promesa sobre datos/IP/discos.

Las pruebas empresariales requieren identidad dedicada y laboratorio explícitamente autorizado; no se adivina tenant, no se reutiliza bootstrap y no se tocan cuotas ni máquinas preexistentes.

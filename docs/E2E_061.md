# IaCoC 0.6.1 — procedimiento E2E real pendiente

Este procedimiento queda preparado para una ventana explícitamente autorizada. No se ejecuta como parte de la validación local y no habilita mutaciones por sí mismo.

## Precondiciones obligatorias

- IACP debe publicar un plan disponible y una Golden Image `certificada` o `habilitada`, autorizada y compatible.
- Debe existir una credencial `reader` para observabilidad y una credencial `operator` dedicada para lifecycle, ambas del mismo tenant.
- La discrepancia de CPU documentada en `docs/IACP_CPU_DISCREPANCY_30030.md` o su evidencia vigente debe estar cerrada por IACP antes de crear.
- La ventana debe autorizar una única KVM descartable en `mng01` o `mng02`; VM 30029, otras VM existentes, plantillas y Golden Images quedan fuera de alcance.
- El operador debe confirmar que el cierre de la prueba incluye eliminación de la KVM creada y conservar el identificador para auditoría.

## Runner

El runner es `scripts/verify-product-gui.mjs`. Solo acepta `baseline` o `read` a través de `scripts/real-e2e-policy.mjs` en el estado actual, por lo que cualquier modo mutante se detiene antes de abrir el navegador. La suspensión se retira únicamente mediante un cambio revisado y una autorización nueva; no se debe introducir un bypass por variable de entorno.

Cuando exista esa autorización, el procedimiento operativo debe:

1. Entregar por stdin al contenedor efímero las credenciales reader/operator desde el gestor autorizado; nunca por argumento, archivo Git, log ni cuerpo de evidencia.
2. Configurar y validar la conexión reader y registrar la credencial operator desde API Connections.
3. Leer el catálogo publicado, seleccionar un plan y una imagen compatible. El runner comprueba autorización, disponibilidad y compatibilidad.
4. Crear una sola KVM con `start_on_create=false`. El payload permitido es comercial: nombre, `plan_id`, `image_id`, red publicada, acceso, arranque y referencias comerciales opacas opcionales. No se envían CPU, memoria, disco, nodo, bridge, VLAN ni otros overrides.
5. Seguir `operation_id` hasta resultado y entrega publicada.
6. Consultar inventario y verificar `instance_id`, `infrastructure_kind=kvm`, VMID no protegido, nodo MNG, imagen y recursos efectivos contra el plan publicado.
7. Ejecutar lifecycle desde la GUI en este orden: Encender, Apagar, Reiniciar, Apagar.
8. Confirmar eliminación por nombre y eliminar la KVM creada.
9. Consultar nuevamente inventario y conservar evidencia `deleted`, operaciones, eventos y timestamps.

## Evidencia producida

`evidence.json` registra, sin secretos:

- `action`, `instance_id`, `operation_id` y timestamp de admisión;
- estado persistido, `normalized_status`, código de error, fase y timestamp de observación;
- VMID, nodo, tipo de infraestructura, imagen y recursos efectivos;
- rutas BFF consultadas, estado HTTP y tiempos de respuesta;
- validación de que el comando de creación no incluyó overrides técnicos.

Las fechas de la interfaz se muestran en `America/Costa_Rica`; los timestamps de evidencia conservan además el valor ISO recibido de IACP.

## Criterio de cierre

El E2E se considera aprobado solo si todas las acciones son admitidas y completadas por IACP, la verificación posterior confirma la KVM real y la eliminación termina en `deleted`. Una respuesta `202` solo acredita admisión. `uncertain`, `failed`, discrepancia de recursos o falta de evidencia de entrega detienen el cierre y no autorizan reenvíos automáticos.
